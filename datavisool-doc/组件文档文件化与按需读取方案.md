# Web 端组件文档文件化与按需读取方案

日期：2026 年 10 月 7 日。状态：Web 端第一版已实现，真实模型联调及正式部署验收待完成。

组件专属文档在开发时与组件实现放在一起；构建时统一收集到文件目录 D，生成文档索引 Index；实际运行时通过 Index 定位文件，按需读取和解析，正文及解析结果不做长期缓存。服务器组件在上传时完成文档收集和索引登记，使用同一读取入口。

本方案仅覆盖 Web 项目的内置组件与服务器组件，涉及文档存放、索引、读取和版本管理。现有完整规格返回契约继续保留，改变的是资料的存储与读取方式。

## 开发时的文档组织

组件专属文档与 Definition、Controller、配置面板和渲染实现放在同一目录，随代码一起修改、审查和迁移。

```text
组件目录/
  ComponentDefinition.ts
  ComponentController.ts
  ComponentConfig.tsx
  Component.tsx
  <组件类型>.md
```

每个组件只维护一份 `<组件类型>.md`，文件名与组件注册的类型标识一致，保留原有大小写，例如 `BaseText.md`、`DateTimePicker.md`。通过章节区分组件选择说明与完整规格：

```markdown
# 组件说明
## 组件标识
## 组件选择
## 完整规格
### 配置字段
### 数据要求
### 校验规则
### 限制与校验
### 公共片段引用
```

“组件标识”声明组件类型及名称；“组件选择”描述用途、适用场景和选择条件；“完整规格”描述配置字段、数据要求、限制、校验规则和示例，示例保留在“限制与校验”章节中。按组件实际能力填写；向 Agent 开放配置的组件必须具备完整规格章节。原有 `AI_SELECTION.md` 与 `AI_OPTIMIZATION.md` 已合并到该文件，共 55 份文档，其中 48 种组件具备完整规格。

G2Plot 公共片段、文档格式规范等公共内容集中维护。构建阶段从公共 Markdown 中提取片段，输出独立 JSON 文件，避免运行时为了一个片段读取和解析整个公共说明。

内置组件只保留组件目录中的可编辑源文件；集中资料目录由构建生成，不再人工维护第二份正文。文档随 Web 组件代码版本管理。

## 文件目录与索引

目录 D 是服务器磁盘上的资料目录。以下结构为目标约定，根路径由部署环境配置，不写死在业务代码中。

```text
D/
  builtin/
    <corpusVersion>/
      index.json
      components/
        BaseText/
          BaseText.md
        DateTimePicker/
          DateTimePicker.md
      common/
        g2plot-axis.json
        g2plot-legend.json
  remote/
    <userId>/
      <componentId>/
        <version>/
          manifest.json
          <组件类型>.md
          common/
            private-fragment.json
```

内置组件使用构建生成的 `index.json`。服务器组件使用数据库中的动态索引，正文仍在 `remote` 文件目录中。Index 表示统一的定位能力，不要求两类索引都维护在同一个 JSON 文件里。

索引只保存必要元数据，不保存 Markdown 正文、完整配置结构或解析后的规则对象。

| 信息 | 用途 |
| --- | --- |
| 来源 `builtin` 或 `remote` | 区分内置组件和服务器组件。 |
| 组件类型、名称及选择摘要 | 支持目录展示和初步筛选。 |
| 组件 ID、所属用户 | 定位服务器组件并延续现有用户隔离。 |
| 文档相对路径 | 定位该组件唯一的说明文档。 |
| 章节标识及起止行 | 在同一文档中定位组件选择、完整规格及其子章节；与文件哈希绑定。 |
| 文件 SHA-256、字节数 | 校验文件一致性，并在读取前检查大小。 |
| 文档格式版本、组件版本、语料版本 | 确定解析协议及代码与文档的对应版本。 |
| 公共片段引用及其路径 | 只读取本次规格需要的片段。 |
| 文档可用状态 | 区分具备完整规格和未携带文档的组件。 |

服务器组件不能仅以组件类型作为索引唯一键。逻辑身份至少包含来源、用户、组件 ID、组件类型和版本；统一查询入口根据当前画布实际加载的组件来源定位，存在歧义时明确报错。

动态索引使用关联 `remote_component` 的 `remote_component_document` 表，保存上述定位字段；不在数据库中存正文。建表及删除方式遵循仓库[开发规范](./开发规范.md)，保留逻辑删除、创建时间和更新时间字段，物理清理由资源清理流程执行。

## 内置组件的构建与部署

1. 扫描组件实现目录中的 `<组件类型>.md`，提取组件类型、选择摘要及章节位置。
2. 校验文件名与注册组件类型、文档声明类型一致，并校验组件类型唯一性、开放组件的文档覆盖、章节结构、JSON、示例及公共片段引用；无效内容使构建失败。
3. 将每个组件的一份文档复制到构建输出目录，将公共片段拆分为独立文件；组件选择与完整规格不另行拆文件。
4. 根据源文档、组件实现及公共片段计算文件哈希、组件代码版本和语料版本，生成 Index。运行时不再扫描整库正文计算版本。
5. 将资料目录作为发布资源交付，并在部署阶段落盘。运行服务启动时只检查索引及版本，不预读或解析全部正文。

Web 发布链路需要将资料文件与服务发布包一起交付，部署到 Java 后端可读取的目录。浏览器通过受控的后端读取入口获取结果，不直接接收服务器物理路径。

开发态与发布构建使用同一个生成程序：启动 Vite 时先生成一次，随后监听文档及组件代码的新增、修改、删除，自动重新生成产物并切换 Index；无效文档不会替换当前有效索引。开发和生产使用同一读取契约，避免开发态重新引入正文的全量缓存。

## 运行时按需读取

Java 后端实现文档读取服务，统一负责索引查询、路径定位、版本校验、文件读取和临时解析。

| 操作 | 读取行为 |
| --- | --- |
| 获取组件目录 | 返回当前可用组件及文档定位信息，只读取索引。 |
| `get_component_document` | 按组件身份或索引提供的相对路径定位组件文档，按章节或行范围返回内容。 |
| `search_component_documents` | 先按类型和摘要筛选，再逐文件扫描正文；限制命中数量和扫描范围。 |
| `resolve_component_specs` | 从选中组件文档的“完整规格”章节组装配置、数据要求、限制和示例，再读取引用的公共片段。 |

`resolve_component_specs` 沿用单次 1–10 种组件、自动去重及 256 KiB 完整响应上限。超限时明确失败并要求缩小范围，不返回截断的“完整规格”。调用者无需手工拼装公共片段。

文件读取只接受 Index 登记的路径，并限制在对应资料根目录内。读取前检查当前用户、组件来源、可用状态和版本，正文读取后检查文件哈希。文件缺失、版本不匹配或格式无效时返回明确错误，不回退到未登记的路径。

搜索采用逐文件读取，完整规格按选中组件逐个处理。单次请求内可以去重公共片段并暂存所需结果；请求结束后读取服务不保留正文或解析结果。普通读取还需设置单次行数、字节数及读取并发上限，避免通过一个请求加载整个资料库。

## 服务器组件的上传与维护

服务器组件包应携带代码、一份 `<组件类型>.md` 和 `manifest.json`，采用与内置组件相同的命名规则及文档章节结构。元信息声明组件类型、组件版本、代码入口、文档格式版本、文档路径及公共片段依赖；服务器不通过执行上传脚本来识别这些信息。

元信息中的组件类型在浏览器注册组件时与实际 Definition 的类型核对。登记的资源版本也需要随组件列表下发，用于确认画布加载的代码与文档属于同一版本。

### 上传

1. 在临时目录保存并解析组件包，校验文档文件名与元信息、文档声明的组件类型一致，并校验代码入口、文档结构及片段依赖。
2. 生成新的资源版本，写入对应组件资源目录及 D 下的文档目录；生成文件哈希。
3. 文件落盘成功后，在数据库事务中登记组件记录和动态文档索引，发布为可用版本。
4. 发布失败时清理本次新建的文件，不留下可查询的无效索引；未发布的临时目录可由清理流程回收。

文件系统与数据库不能组成同一个普通数据库事务，因此使用“先落盘，后发布索引”的顺序。只有成功发布的记录可以被目录查询和读取服务发现。

服务器组件可以引用明确版本的公共片段；组件自己的公共片段随包上传，并登记在该组件版本下，不覆盖内置片段。

### 替换

替换时创建新的代码和文档目录，校验成功后一起切换当前版本。新请求使用新版本；已加载旧代码的画布不能自动改读新文档，需要按其可信的资源版本定位旧文档，或提示重新加载组件。

旧文件按组件、项目和任务的引用情况清理，避免文件替换使正在运行的任务读取到不同版本的说明。

### 删除

逻辑删除组件时同步停用其动态文档索引，新查询和读取不再返回该组件。正文文件随组件资源的既有引用检查与清理流程回收，不在索引停用后继续绕过权限读取。

### 导入导出与历史组件

项目导入导出需要一并处理组件文档和元信息；导入成功后登记动态索引，并改写为导入后的资源路径。

已有脚本及无文档的组件包继续保留普通使用能力，登记为“无完整规格文档”；Agent 不将其列为可配置组件，也不凭缺失文档生成配置。上传补齐文档的新版本后再开放相应能力。

## 版本与内存边界

每次任务绑定它实际使用的组件身份、代码版本和文档版本。完整规格读取成功后记录组件身份、`create` 或 `patch` 意图及资料版本；失败、缺失、截断和哈希不一致的结果不能授予完整读取证据。

后续写入校验必须与对应组件版本的证据一致。需要具体规则时，由校验服务再次按路径读取并临时解析；不为维护证据建立长期保存整份正文或完整规则对象的缓存。

修改已有组件的数据或字段映射前，必须调用 `get_component_data_contract`，指定目标组件及本次目标 `sourceType`。后端在成功回执中按需读取对应文档，补入真实数据能力和专属要求，并把契约随任务操作记录持久化；写入时仅查询本任务中该组件最近一次成功契约，核对组件类型、文档版本、数据源分支和最终字段映射。切换数据源须重新读取说明书；纯样式、图层及滤镜修改无需数据说明书。样式规则校验包含路径、联合类型、枚举、数值范围、数组元素及数量和函数配置，正文及规则仍不进入长期内存缓存。

常驻数据限于必要的内置目录元信息和轻量定位信息。服务器组件目录通过数据库按用户和查询范围获取，不在启动时把所有用户的动态索引加载到内存。索引仍会随组件数量增长，但正文工作集由单次读取量和并发上限控制。

Agent 本轮读到的工具结果仍会进入任务上下文，任务记录也可以持久化到数据库或磁盘；这部分使用现有上下文预算、压缩及历史分页控制。文件化消除的是整库正文和全局解析缓存，不能代替任务上下文的容量管理。

请求结束后不再保留正文引用；实际内存回收由 Java 垃圾回收机制决定。验收关注长期引用与受控工作集，不要求进程内存占用在每次读取结束后立即下降。

## 第一版试用与部署

开发时在 `frontend` 目录执行 `pnpm -F lcp-web-app dev`。内置资料默认目录为 `backend/lcp-server/target/component-docs`，上传文档默认存到项目资源根目录下的 `component-docs/remote`，避免清理构建产物时删除运行数据；第一次更新代码后需重启前端开发服务及 Java 后端，后续文档修改由开发监听自动处理。后端启动时按现有迁移配置创建 `remote_component_document` 表。

可单独执行 `pnpm -F lcp-web-app docs:generate` 生成资料。`build` 和 `action` 自动执行同一生成规则；Maven 发布构建通过现有前端构建步骤生成资料。

发布时将 `target/component-docs` 整个目录与服务 JAR 一起交付，放在服务器运行目录的 `component-docs` 下。Dockerfile 已增加复制步骤。可以通过 `datavisool.component-docs.root` 配置根目录，或在前后端进程中设置同一个绝对路径的 `DATAVISOOL_COMPONENT_DOCS_ROOT`；显式配置后，内置与上传文档统一存到该根目录下。发布构建产物只交付内置资料，运行中的上传文档作为持久化数据保留。资料正文不打入前端 JavaScript，也不作为 JAR 内的正文资源交付。

服务器组件的 ZIP 包示例：

```text
RemoteText.zip
  manifest.json
  entry.js
  RemoteText.md
```

```json
{
  "componentType": "RemoteText",
  "componentVersion": "1.0.0",
  "codeEntry": "entry.js",
  "documentFormatVersion": "component-document/v1",
  "documentPath": "RemoteText.md",
  "commonFragments": {}
}
```

`componentVersion` 是作者声明的组件版本；后端另生成不可变资源版本，绑定代码入口与文档索引。“公共片段引用”存在依赖时，在 `commonFragments` 中声明标签到包内 JSON 文件的相对路径；引用内置片段时还需声明 `builtinCorpusVersion`。上传阶段会固定相关片段文件及包内引用，导入导出可以携带这些依赖。

调用链为：Agent 工具 → 浏览器提供当前已加载组件身份 → `/api/component-documents/{operation}` → Java 查询索引并读文件 → 返回工具结果。完整规格证据保存在任务操作记录中；后续创建及配置补丁读取相应版本的规则进行校验，浏览器再次核对实际加载代码的版本。

内置索引约 102 KiB，正文与公共片段约 722 KiB；这些是当前构建产物大小，不代表堆内存测量结果。验证包含真实 Vite 文档监听、48 种规格读取、章节分页、文件修改后不复用旧解析结果，以及基于 H2 的服务器组件生命周期测试。

## 验收标准

| 场景 | 必须满足的行为 |
| --- | --- |
| 文档组织 | 每个组件只维护和发布一份 `<组件类型>.md`，文件名与组件类型一致，选择说明与完整规格通过章节区分。 |
| 启动与首屏 | 不读取或解析整库正文，不将正文嵌入前端 JavaScript。 |
| 单组件规格请求 | 只读取该组件文档及引用的公共片段，配置、限制和示例与改造前一致。 |
| 重复读取 | 每次按需读取；读取服务没有随请求次数累积正文或解析对象的全局缓存。 |
| 文档规模增长 | 增加未访问组件的文档，不扩大正在运行任务的正文工作集。 |
| 搜索与并发 | 逐文件扫描、结果及读取量受限，多个请求的临时内存受并发上限约束。 |
| 完整规格超限 | 明确失败，不返回截断规格，不记录完整读取证据。 |
| 缺失或失效文档 | 文件缺失、哈希不符、格式错误及版本不匹配均返回明确错误。 |
| 上传与替换失败 | 原可用版本保持有效，新失败版本不进入可用索引。 |
