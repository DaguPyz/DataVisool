# 一、架构内核设计

## 1.1 内核设计

流程可以分为 **登记 → 激活 → 运行 → 停用清理**。

1. **登记**：把插件实例交给内核，由内核检查声明和依赖。
2. **激活**：内核调用 `activate`。插件在这里登记能力和事件订阅，激活成功后它们才生效。
3. **运行**：插件通过已登记的能力和事件协作。
4. **停用清理**：先做退出准备，再调用可选的 `deactivate`
   ，撤销能力和订阅。[Lodestory 内核实现](/Users/yinzhenpu/projects/Lodestory/src/plugin-core/EngineCore.ts)



## 1.2 登记

对。每个插件声明自己的 `id`、依赖的能力（`requires`）、提供的能力（`provides`），以及启动入口 `activate`
。应用入口把插件实例统一交给内核，内核据此生成一份待启动的插件清单（记为：PluginList），用于检查依赖和确定激活顺序。

建议把 **provider** 设计成「能力标识 `key` + 可调用的服务 `service`」。以项目存储为例，服务对外提供 `load` 和 `save`。

```ts
interface ProjectStorage {
  load(projectId: string): Promise<ProjectData>;
  save(projectId: string, data: ProjectData): Promise<void>;
}

const projectStorageKey = createServiceKey<ProjectStorage>("project/storage");

// 提供方在 activate 中登记
context.provide(projectStorageKey, { load, save });

// 使用方通过同一个 key 取得并调用
await context.get(projectStorageKey).save(projectId, data);
```

插件在 `provides` 里声明 `key`，激活时交付服务实现。内核自动记录它属于哪个插件，停用时据此撤销。

## 1.3 激活

内核先用 `requires` 和 `provides` 匹配依赖，再按顺序调用插件的 `activate`。有三个细节：

1. **循环依赖会报错并中止整批启动。** 会报出 `A → B → A` 这样的循环链。缺少必需能力、插件 ID 重复、同一能力有多个提供者，也会在激活前报错。
2. **提供者激活成功后，使用者才启动。** 内核会等 `activate` 执行完，并确认承诺的能力都已登记。多个插件同时满足条件时，按清单顺序启动。
3. **中途失败会回滚。** 先清理失败插件已分配的资源，再按启动的逆序清理本批已激活的插件。
4. **懒加载机制** 激活之后只代表插件可用，但并不意味着就一定要加载当前插件的所有内容，可以等到真正使用这个插件的时候再加载他的所有资源

## 1.4 运行

运行时，用户操作或事件触发已登记的入口，执行对应的插件代码。


### 1.4.1 事件机制

建议用 **共享事件标识 + 事件数据**。比如项目插件保存成功后发出 `projectSaved`，项目列表收到 `projectId` 后刷新对应条目。

DataVisool 启动时创建一个内核，由这个内核持有一个事件容器 `EventBus`。容器以事件标识中的唯一值 `symbol` 为键，存放该事件的订阅列表，结构为 `Map<symbol, EventSubscription[]>`。每条订阅记录包含订阅插件的 ID、监听函数和状态（待生效、已生效、已取消）。

```ts
const projectSaved = createEventKey<{ projectId: string }>("project/saved");

// 列表插件在 activate 中订阅
context.on(projectSaved, ({ projectId }) => refreshProject(projectId));

// 项目插件在保存成功后发布
void context.emit(projectSaved, { projectId }).catch(reportEventError);
```

- `on` 将订阅加入对应列表并返回取消函数。订阅在激活成功后生效，回滚或停用时，内核按插件 ID 撤销该插件的订阅。撤销时将记录标记为已取消并移出列表。
- `emit` 查找该事件已生效的订阅，按订阅顺序逐个等待执行，并跳过执行前已取消的监听。某个监听失败时继续通知其余监听，最后汇总通知错误。没有订阅者时正常结束。[Lodestory 事件总线](/Users/yinzhenpu/projects/Lodestory/src/plugin-core/EventBus.ts:49)

## 1.5 停用清理

关闭应用或插件的时候清理对应插件所依赖的内存、存储等资源

1. **检查依赖。** 还有插件在依赖它时，拒绝单独停用。关闭应用时，先停依赖方，再停能力提供方。
2. **准备退出。** 暂停新的用户操作和事件投递，等正在执行的任务结束或取消，再处理未保存的修改。用户取消或保存失败时，恢复操作并保留编辑现场。
3. **撤回入口。** 移除插件登记的菜单、面板、快捷键等入口，等界面卸载完成。撤回失败时保留服务和数据，允许重试。
4. **释放资源。** 调用 `deactivate` 清理定时器、外部监听、网络连接、渲染对象和临时缓存。项目文件和用户配置按保存流程保留。
5. **清除内核记录。** 内核撤销 `provider`、事件订阅和依赖记录，使插件上下文失效。资源清理出错时，继续处理其余清理项，最后汇总错误。[Lodestory 停用实现](/Users/yinzhenpu/projects/Lodestory/src/plugin-core/EngineCore.ts:317)

# 二、插件的内容边界

1. **内容归属。** 插件是独立的代码单元，持有完成自身职责所需的页面、专用组件、业务逻辑、私有状态、样式、资源和生命周期清理逻辑。
2. **唯一入口。** 插件只向应用入口公开一个创建函数。应用入口调用它取得插件实例，再交给内核登记。
3. **依赖声明。** 插件之间的依赖限于公共契约。插件在 `requires` 中声明必需的能力，在 `provides` 中声明对外提供的能力，由内核在激活前检查依赖。
4. **通信与契约。** 内核通过插件上下文提供能力的注册与获取、事件的发布与订阅。能力接口及其标识、事件数据及其标识由对应的能力提供方或事件发布方定义和维护，统一放在插件实现目录之外的公共契约模块。需要执行操作并取得结果时调用能力，通知已发生的变化时发布事件。
5. **共享边界。** 插件可以直接复用请求、加密等通用库。跨插件使用的业务状态由明确的所有者维护，其他插件通过公开能力访问。

## 禁止事项

- 禁止插件公开创建函数以外的源码入口。禁止导入其他插件实现目录内的模块，包括其创建函数，也禁止通过公共模块间接引用这些模块。
- 禁止把插件专用的页面、资源或业务逻辑放在插件实现目录之外。禁止在内核、公共契约模块或通用库中维护共享业务状态。
- 禁止使用未在 `requires` 中声明的必需能力，或用固定的启动顺序代替依赖声明。
- 禁止绕过内核进行跨插件通信，例如通过全局变量、共享单例或自建事件总线调用其他插件或交换数据。
- 禁止直接读写其他插件管理的状态、缓存或持久化数据。
- 禁止用事件替代需要取得执行结果的能力调用。

# 三、代码结构

内核命名为 **Visloom**，实现目录为 `datavisool-app/src/visloom/`。

```text
visloom/
├── index.ts               # 对外导出 Visloom、插件接口和标识创建函数
├── Visloom.ts             # 调度插件生命周期，维护已激活的插件
├── PluginList.ts          # 生成待启动清单，检查依赖并确定激活顺序
├── ProviderRegistry.ts    # 按能力标识保存服务，记录它由哪个插件提供
├── EventBus.ts            # 保存订阅、派发事件、按插件撤销订阅
└── contracts/
    ├── Plugin.ts          # 定义 Plugin、PluginContext 和生命周期接口
    ├── ServiceKey.ts      # 定义能力标识和 createServiceKey
    └── EventKey.ts        # 定义事件标识和 createEventKey
```

`Visloom.ts` 持有 provider 注册表和事件容器。应用入口负责选定插件并交给 Visloom。`projectStorageKey`、`projectSaved` 等具体标识由对应业务的公开契约定义。
